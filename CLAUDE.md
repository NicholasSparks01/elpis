# Elpis — notes for Claude Code

Elpis runs coding agents in microVM sandboxes on Windows: an OCI container inside a libkrun VM on Windows Hypervisor Platform (WHP). Rust workspace, Apache-2.0. Read `docs/architecture.md` before larger changes and `docs/vmm.md` before touching the shim or libkrun.

## Build, test, lint

Run in Git Bash from the repo root.

```bash
./scripts/fetch-libkrun.sh          # once, and after changing the pin or patches/libkrun/*
cargo build --release --locked
cargo test --release --locked
cargo clippy --release --locked
```

- `third_party/libkrun` is generated by the script; never edit it directly and never commit it.
- `./scripts/build-guest.sh --install` builds the guest kernel and rootfs in Docker (slow; only for `guest/` changes) and copies them beside `target/release/elpis-shim.exe`.
- The code isn't rustfmt-formatted; don't run `cargo fmt` over the tree (it would rewrite every file). Match the surrounding style: long lines (~150), terse comments that say *why*.
- CI (GitHub-hosted Windows) builds, tests and lints but **cannot boot VMs** (no nested WHP).

## Rules

- **Independence.** Never copy code, binaries, config or text from Docker Sandboxes (sbx) or other proprietary software. sbx compatibility is through public behaviour only.
- **Names.** "nerdbox" means upstream containerd/nerdbox only: `io.containerd.nerdbox.*` annotations, `nerdbox.services.*`, `containerd-shim-nerdbox-v1`, sbx's `nerdbox-kernel`/`nerdbox-rootfs` files. Everything of ours is `elpis` / `ELPIS_*`.
- **Attribution.** Code ported from containerd/nerdbox or libkrun says so in a comment and is covered in `NOTICE`.
- **libkrun changes** are new or updated patches in `patches/libkrun/` with a description of the problem; keep them small and upstreamable.
- **Security-sensitive areas:** `netstack.rs`, `policy.rs`, `credproxy.rs`, `secrets.rs`, the shim's device setup, the libkrun patches. Prefer secure defaults, add tests, and update `docs/security.md` when behaviour changes.
- **Docs move with code.** A changed command, option, default, file or env var updates `README.md` / `docs/` in the same change.
- No personal data (names, e-mails, user paths, box names) in code, docs or tests. Use `C:\Users\me\...`, `mybox`.
- Errors use `anyhow::Context` and tell the user what to do next.

## Gotchas

- ttrpc stream IDs must be allocated **under the writer lock** (`ttrpc.rs`), or concurrent calls hit "StreamID cannot be re-used".
- The guest needs **ACPI** on WHP even with virtio-mmio. libkrun's `hvc0` only works via `add_default_console`; console output lands in `bundle\vm\krun.log`.
- virtio-mmio is the default; virtio-pci (`ELPIS_VIRTIO=pci`) depends on patch 0003.
- virtio-fs shares need absolute host paths; `CachePolicy::Never` + `LinuxSimplified`.
- The container MAC must differ from the NIC MAC; `io.containerd.nerdbox.ctr.dns` is written verbatim to resolv.conf (`nameserver 172.17.0.0\n`).
- Writable layers need an ext4 journal (`-j`), or a hard stop can corrupt them.
- The proxy CA is regenerated when its CN differs from `CA_NAME`.
- In the guest build, glibc tools need `libgcc_s` copied in.
- Never boot two VMs on the same box folder.

## Verifying VM-level changes

Unit tests don't cover booting, disks, networking or the guest. On a Windows machine with WHP and the guest built:

```bash
target/release/elpis-run.exe create mybox --image alpine:3.20
target/release/elpis-run.exe exec mybox -- sh -c "uname -a && wget -qO- https://example.com | head -1"
target/release/elpis-run.exe rm mybox
```

`elpis-shim -id x boot-test` (run in a box's `bundle` folder) boots exactly as Create would. Say in the PR what was run on a real box, or that it wasn't.
